# Hermes Agent

Persistent AI gateway with a web dashboard, an OpenAI-compatible API, skills, and memory. Ships in the default **`core`** profile.

[Hermes Agent](https://github.com/NousResearch/hermes-agent) runs as a persistent AI gateway with a web dashboard. It divides the work with OpenCode: Hermes takes messaging integrations and general agent workflows (skills, memory, scheduled jobs), while OpenCode sticks to coding in an isolated sandbox (`coding` profile). With `coding` enabled, Hermes can also **delegate** coding jobs to OpenCode via `opencode-mcp` (`coding_*` tools) so the user stays in Hermes — see [OpenCode — Hermes delegation](opencode.md#hermes-delegation).

## Enabling Hermes

Hermes starts whenever `core` is in `COMPOSE_PROFILES` (setup sets this by default):

```bash
# In .env (see .env.example)
COMPOSE_PROFILES=core
```

Then:

```bash
docker compose up -d
```

Remove `core` from `COMPOSE_PROFILES` to turn Hermes off. If it is already running, also run `docker compose down` or `docker compose stop hermes hermes-webui`.

You can combine profiles (`COMPOSE_PROFILES=core,rag,searxng-prod` or `--profile core --profile rag`).

## First-time setup

1. Run `./scripts/setup.sh` (creates Hermes env files and sets `COMPOSE_PROFILES=core`).
2. Run the setup wizard (writes config to `data/hermes/` on the host):
   ```bash
   docker compose run --rm hermes setup
   ```
3. Start the stack (bootstrap runs automatically, then the gateway):
   ```bash
   docker compose up -d
   ```
4. Open `http://localhost:9119` for the dashboard and sign in with `HERMES_DASHBOARD_USER` / `HERMES_DASHBOARD_PASSWORD` from `.env` (generated by `setup.sh`). `make dashboard-open` opens it signed in, through a link that works once within 60 seconds; `make dashboard-open NEXT=/kanban` lands on the board. Link details are in [extending.md](extending.md#dashboard-links).

   Since agent 0.20.0 those credentials are mandatory rather than a hardening option. Inside the container the dashboard binds `0.0.0.0` (the host port is what keeps it local), and a non-loopback bind engages an auth gate that the old `HERMES_DASHBOARD_INSECURE=1` escape hatch no longer opens. With no auth provider registered the dashboard refuses to bind at all, and since the `hermes` healthcheck probes the dashboard, the container never turns healthy. The healthcheck also probes the api-server gateway on 8643, which answers only after startup MCP discovery has finished for every profile.

5. Chat UI is included on `core`: see [docs/hermes-webui.md](hermes-webui.md) (`http://localhost:8787`).

**Migrating from root `.env` API settings:** if you previously set `API_SERVER_ENABLED`, `API_SERVER_HOST`, or `API_SERVER_KEY` in `.env`, remove those lines and move `API_SERVER_KEY` into `compose/hermes/api-server.env`. The default profile exposes an API on port 8642 only under `HERMES_GATEWAY_TOPOLOGY=multiplex` ([Gateway topology](#gateway-topology)).

The `hermes` container does not load the root `.env`. Its environment is an allowlist: dashboard basic auth, API timeouts, timezone, the write root, and `HERMES_BUZZ_ENABLED` / `BUZZ_RELAY_URL` for the Buzz localhost proxy. Postgres, n8n, Neo4j, OpenCode, LightRAG, and model keys stay on the services that use them. `SEARXNG_URL` is set empty so native web search cannot bind. Signal and Buzz private keys stay in `data/hermes/` profile env files. The dashboard password is still visible inside this container, because the dashboard runs in the same process environment as the agent.

Host ports for Hermes, the WebUI, LightRAG, Neo4j, n8n, and OpenCode are published on `127.0.0.1`. After changing the allowlist, recreate the containers so they drop the old environment: `docker compose up -d --force-recreate`.

## Image pins (minimum agent tag)

This stack pins Hermes Agent and Hermes WebUI together. The same values live in `.env.example` and as the compose `${…:-…}` fallbacks in `docker-compose.yml`:

| Image | Minimum / default tag |
|---|---|
| `nousresearch/hermes-agent` | **`v0.23.1`** |
| `ghcr.io/nesquena/hermes-webui` | **`0.52.544`** |

Bump both with `make hermes-upgrade AGENT=… WEBUI=…` — never one at a time. Details: [Hermes WebUI — Upgrading](hermes-webui.md#upgrading).

After a bump, `make hermes-image-test` runs every overlay and bootstrap test inside the new image and fails if the image is missing. The tests read the tag from `docker-compose.yml`; set `HERMES_AGENT_IMAGE_TAG` to test another one. CI runs only their host parts; `.github/workflows/hermes-image.yml` runs the image parts on demand and when the overlays change.

Hermes Agent switched from calendar tags (`v2026.9.14`) to semver (`v0.21.6`, `v0.22.0`, …) after September 2026. A semver tag is newer than every calendar tag, so compare versions by release date, not by string order. The overlays apply to `v0.22.7` and `v0.23.1` (where an anchor changed between them, the patch accepts both shapes) and not to calendar-tagged images.

### Gateway topology

Hermes v0.22 runs one gateway per container that serves every profile, and moves each profile's API server onto the default listener at `/p/<profile>/`. `HERMES_GATEWAY_TOPOLOGY` in `.env` picks the layout. Both keep Boundary's documented ports.

| | `standalone` (default) | `multiplex` |
|---|---|---|
| Gateway processes | one per profile that ran one before | one for all profiles |
| api-server | own listener on 8643 | `:8642/p/api-server/`, and 8643 through `gateway-compat-proxy` |
| browser (WebUI) | own listener on 8644 | `:8642/p/browser/`, and 8644 through `gateway-compat-proxy` |
| Default profile API | none | `:8642/v1`, with its own `API_SERVER_KEY` in `data/hermes/.env` |
| Profiles that never ran a gateway | idle | parked once (`gateway.parked`) |

`compose/hermes/019-pin-profile-gateways.sh` runs before the image's profile reconciler on every start. Under `standalone` it writes `gateway.standalone: true` into each named profile's `config.yaml` where the key is unset, so a profile that ran a gateway before still starts one and a profile that never did stays idle. Upstream calls `gateway.standalone` a temporary compatibility setting that will be removed.

Under `multiplex` it writes no pins. It generates `API_SERVER_KEY` in `data/hermes/.env` if missing, because the default profile owns the only listener and Hermes opens it only with a key. It parks each named profile with no `running` gateway state (writes `gateway.parked`, as `hermes -p <name> gateway stop` does) and records it in `data/hermes/gateway_topology.json`, so a profile you later start with `hermes -p <name> gateway start` is not parked again. The default key reaches the default profile's full toolset, so treat it like the dashboard password. `gateway-compat-proxy` (an s6 service in the `hermes` container, `compose/hermes/gateway-compat-proxy.py`) forwards 8643 to `/p/api-server/` and 8644 to `/p/browser/`, streaming responses and passing `Authorization` and WebSocket upgrades through. Each profile's key works only on its own prefix, and Hermes rejects a profile key shorter than 16 characters there. The WebUI, n8n and `tool-eval.sh` keep their URLs. Under `standalone` the proxy's slot stays down.

Switch with `./scripts/gateway-topology.sh multiplex` (or `standalone`). It clones `data/hermes` to `data/hermes.bak-<time>`, stops `hermes` and `hermes-webui`, sets `gateway.standalone` to `false` (or `true`) on every named profile, writes `HERMES_GATEWAY_TOPOLOGY` to `.env`, and starts both again. `make doctor` then checks the listener, both prefixes and both proxy ports. Before switching, `make gateway-preflight` runs Hermes' migration preflight (`hermes gateway migrate --multiplex --dry-run`) against a temporary copy of the Hermes home with `gateway.standalone` removed, and prints its plan and any blockers without changing the live home. Don't run `hermes gateway migrate` without `--dry-run`: it uninstalls the per-profile gateways and has no rollback.

`make hermes-upgrade` runs `scripts/check-hermes-standalone.sh` and refuses an agent tag without `gateway.standalone` while the topology is `standalone`, since on such an image 8643 and 8644 would stop answering. `HERMES_PIN_STANDALONE_GATEWAYS=0`, the older setting, means `multiplex` when `HERMES_GATEWAY_TOPOLOGY` is unset.

v0.22 gateways also find each other through a control socket at `$HERMES_HOME/gateway.sock`. `data/hermes` is a virtiofs mount on Docker Desktop, where connecting to a Unix socket fails, so each profile gateway restarted in a loop trying to replace the default one. `patch-control-socket-tmp.py` with `HERMES_CONTROL_SOCKET_IN_TMP=1` (set on the `hermes` service) binds those sockets at `/tmp/hermes-gw-<hash>/control.sock` in the container instead, and leaves a `gateway.sock.path` pointer in each home. Since v0.22.3 the gateway refuses a socket whose directory is not private (0700, owned by the gateway user), and `gateway run --replace` accepts a pointer only to that `hermes-gw-<hash>/control.sock` layout.

### Session pruning

With `sessions.auto_prune: true`, Hermes deletes ended sessions that have been inactive for `sessions.retention_days` (90) when it starts. The default was `true` up to v0.22.2 and is `false` from v0.22.3, which instead asks once when the disk is low until the key is written. The same cont-init script writes `sessions.auto_prune: false` into the default profile and every named profile where the key is unset, so `session_search` and the WebUI keep all history. A value you set by hand is left alone. `HERMES_PIN_SESSIONS_KEEP=0` turns the pin off for new profiles.

Dashboard JSON-RPC clients (for example Boundary over the gateway WebSocket) can rely on this agent tag for:

- `timestamp` and `row_id` on `session.history` / `session.resume` transcript rows
- `prompt.submit` truncation: `truncate_before_row_id` (preferred), `truncate_before_message_id`, or `truncate_before_user_ordinal`, with `confirm_truncate`; result may include `survivor_row_id_map`
- `session.branch` (fork a live session into a stored child) and `parent_session_id` on `session.create` / session list rows

For named agent profiles, the optional `profile` parameter picks the profile on `session.create`, `session.resume`, `session.history` and session lists. It does not switch profiles per turn. A session's profile (SOUL, memory and `state.db`) is fixed when the session is created or resumed. With this stack's overlay (below), `prompt.submit` accepts `profile` only when it names that same profile; any other profile is an RPC error (`4081`, with `data.session_profile`) and nothing runs. A room with several agents needs one session per agent profile. Older installs without these `.env` lines now get the same defaults from compose.

This stack also overlays a **per-session history budget** on that agent tag. It is not an upstream Hermes API. `session.create` and `session.resume` take `history_budget`, a positive integer of tokens. The default is no budget: omit the field on create, or send `null`, and Hermes compacts only against the model window, as today. On resume, omitting the field keeps the stored budget and `null` clears it. `0`, negatives, or non-integers are an RPC error (`4028`) that does not change the session. There is no profile config key: a personality profile also runs side chats, and a profile cap would shrink those too.

The budget is a prompt window. Older rows stay in `session.history`. When the history that would be sent exceeds the budget, Hermes keeps a newest-first tail and may prepend a compression summary of the excluded prefix. The summary counts toward the budget. The system prompt, memory, and tool definitions do not. Two cases can report `history_tokens` above the budget: the newest user message is always sent, and an assistant tool call is never split from its tool results.

Once the overlay is running, `session.context_breakdown` and `message.complete` always include:

| Field | Meaning |
|---|---|
| `history_budget` | The session budget, or `null` when unset |
| `history_tokens` | Tokens of history sent (verbatim tail plus summary) |
| `history_first_row_id` | First transcript row included verbatim |
| `history_summarised` | `true` when rows before that point are represented by a summary |

`history_budget: null` means no horizon. `session.context_breakdown` is the cut for the **next** reply, including on open. `message.complete` is the cut **that turn actually sent**. Draw a line only when `history_budget` is a number and either `history_summarised` is true or `history_first_row_id` is not the first row of `session.history`.

### Client context

A second overlay lets a dashboard client tell the agent where a conversation is happening, such as a room's name, its members, or which member is answering, without putting that in the user's message. It is not an upstream Hermes API. Clients that leave it out see no change.

| Where | Field | Effect |
|---|---|---|
| `session.create`, `session.resume` | `context` (string or `null`) | **Session context.** Added to the system prompt on every turn, under a `Client Session Context` heading. Not stored. On resume, omitting the field keeps the live session's value and `null` or an empty string clears it. A session rebuilt after a gateway restart has none until the client sends it again. |
| `prompt.submit` | `context` (string) | **Turn context.** Added to that turn's model input after the user's text, under a `Client Turn Context` heading. It never appears in `session.history`. |

Both headings come with a line telling the model to treat names and labels in the block as untrusted metadata. Turn context uses the same channel as Hermes' own per-turn notes. It is stored in the user row's `api_content` sidecar in `state.db` and sent again on later turns, which keeps the prompt cache warm and means the model still knows who was addressed earlier. Use session context for anything that holds for the whole conversation, because changing it changes the system prompt and costs one prompt-cache miss.

Errors (the session is not changed):

| Code | When |
|---|---|
| `4080` | `context` is not a string or `null`, or is longer than 16,000 characters |
| `4081` | `prompt.submit` names a different `profile` from the session's (see above) |
| `4082` | `prompt.submit` with `context` while a turn is running. Context cannot be queued, steered or redirected, so resubmit after `message.complete`, or check [`session.live_status`](#turn-liveness) first and send once it reports `running: false`. |
| `4083` | Context on a session whose turns run in an isolated compute-host worker (`dashboard.turn_isolation`, off by default) |

`gateway.capabilities` adds `client_context: true` and `prompt_profile_check: true` when this overlay is installed. Check them before sending `context`, so the same client still works against an unpatched gateway, which answers an unknown `context` field with `4000`.

#### Platform hints

Hermes adds a short platform hint to the system prompt based on the session's `source`. It has built-in hints for `cli`, `tui`, `desktop`, the messaging platforms and a few others. Any other `source`, such as Boundary's `boundary`, gets no hint by default. A client can describe itself with `agent.platform_hints.<source>` in the `config.yaml` of each profile that serves it:

```yaml
agent:
  platform_hints:
    boundary: >-
      You are chatting inside the Boundary desktop app. Replies render as Markdown.
```

A bare string is appended to the built-in hint, or used on its own when there is none. `{replace: "..."}` swaps out a built-in hint and `{append: "..."}` adds to it. Each profile reads its own `config.yaml` (`data/hermes/config.yaml` for the default profile, `data/hermes/profiles/<name>/config.yaml` for the others), so set the hint in every profile the client uses. For text that changes between sessions, use session context instead.

### Speaker names

An overlay lets a client run several agents in one session and name who answers each turn. It is not an upstream Hermes API. Upstream's turn `author` labels only the user side of a turn, for memory, and a client can't set it on `prompt.submit` (`4124`).

`speaker` on `prompt.submit` is `{id, display_name}`. Either field may be left out, but not both. Each is a string, cleaned like upstream's turn authors (control characters dropped, 200 characters at most), with `[` and `]` turned into `(` and `)`. `null` or omitting the field means no speaker.

What a turn with a speaker changes:

- **History:** each assistant row with text that the turn writes gets `display_metadata.speaker` (the cleaned object), which `session.history` returns. Rows from turns without a speaker have none.
- **Model input on later turns:** those rows are sent to the model with a first line `[speaker: Ada (ada)]` (display name, then id when it differs; one of them when only one is set). The label is written to the row's `api_content` sidecar in `state.db` when the row is first stored, so every later request sends the same bytes, after a resume too, and the prompt cache holds. `session.history` text doesn't include it. Assistant messages that only call tools carry no label.
- **That turn's input:** a note under a `Speaker` heading, sent through the same per-turn channel as turn context, names the speaker and tells the model about the labels.
- **Copied labels:** if the model starts its reply with a `[speaker: ...]` line anyway, that line is removed from the stored row. The live `message.delta` stream isn't changed.

Errors (the session is not changed):

| Code | When |
|---|---|
| `4084` | `speaker` is not an object or `null`, has a field other than `id` and `display_name`, has a non-string field, or has nothing left after cleaning |
| `4085` | `speaker` while a turn is running. A speaker cannot be queued, steered or redirected. Resubmit after `message.complete`. |
| `4086` | `speaker` on a session whose turns run in an isolated compute-host worker |

`gateway.capabilities` adds `turn_speaker: true` when this overlay is installed. Check it before sending `speaker`, because an unpatched gateway answers the unknown field with `4000`.

### Turn liveness

Another overlay lets a dashboard client tell a slow turn from a lost one without polling. It is not an upstream Hermes API. Upstream sends `session.usage` only when token counts change, so a single slow model call, such as a local model reading a long prompt, can be silent on the wire for minutes.

**`turn.heartbeat`** is an event sent every `HERMES_TURN_HEARTBEAT_S` seconds (default `30`, `0` turns it off) while a session's turn runs, whatever else is streaming. It comes from the same thread as `session.usage`, which the turn stops before `message.complete`, so none arrives after the turn ends. The frame's `session_id` is the gateway session id, as on every event. The payload has no transcript content:

| Field | Meaning |
|---|---|
| `running` | Always `true` |
| `status` | `working`, or `waiting` while an approval or clarify prompt is open |
| `turn_started_at` | Epoch seconds the turn started |
| `idle_s` | Seconds since the agent last recorded activity (an API wait, a stream chunk, tool progress), or `null` when unknown. Hermes aborts a turn whose activity clock stays idle for `agent.turn_liveness.timeout_s` (600 s by default) and then sends the usual completion. |
| `interval_s` | The heartbeat interval. A client can treat roughly two missed intervals as a lost stream. |

**`session.live_status`** returns one session's live state from memory: no database read, no title, no preview. Params: `session_id` (gateway id) and/or `session_key` (stored id), and optional `profile`. Without `profile` a session in any profile matches, as in `session.active_list`. With it, only that profile's sessions do, and an unknown profile is `4064`. The result is `{session_id, session_key, status, running, turn_started_at, idle_s}`. `status` uses the same values as `session.active_list` items. A session that is not live (closed, reaped, or never opened in this process) answers `status: "idle"`, `running: false` and `null`s, never an error. Sending neither id is `4006`.

**`gateway.capabilities`** adds `turn_heartbeat` (bool), `turn_heartbeat_s` (seconds) and `session_live_status: true`. Check them before relying on either feature, so the same client still works against an unpatched gateway.

### The reply a client shows

`message.complete.text` is the turn's final reply. `message.delta` frames are a preview of it, and some turns send none: a profile with a plugin that holds the stream (a `hold_stream` transform) shows its reply only in `message.complete`, and so does a tool-loop guardrail stop in such a profile. This stack loads no such plugin, so a guardrail stop also streams as deltas here. A client that builds the reply from deltas shows `text` when no delta arrived, with two exceptions: `response_previewed: true` means the reply was already shown as a `message.interim`, and a bot-mode session sends `text: ""` when it withheld a silence marker, in which case the streamed text stands. `response_transformed: true` means `text` replaces whatever streamed. Upstream sends these fields; this stack doesn't change them.

## API server profile (`api-server`)

A one-shot `hermes-api-bootstrap` service runs ahead of the main Hermes container, creating or updating an isolated **`api-server`** profile with:

| Setting | Value |
|---|---|
| Port | **8643** (`HERMES_API_SERVER_PORT`) |
| Max tool turns | **20** (`HERMES_API_MAX_TURNS`) |
| Tool-loop hard stop | **on** for every profile (`HERMES_TOOL_LOOP_HARD_STOP`): a turn ends after 5 back-to-back repeats of the same call, 5 laps of an identical cycle of up to 4 calls, or the third time it re-runs one call and gets back a result it had already seen that turn (any cycle length; pollers exempt) |
| Tools | **`hermes-api-server`** (aligned with dashboard chat; no interactive-only tools) |
| Default profile API | none under `standalone`; `:8642/v1` under `multiplex` ([Gateway topology](#gateway-topology)) |

| Endpoint | URL |
|---|---|
| Host API | `http://localhost:8643/v1` |
| Compose network (n8n) | `http://hermes:8643/v1` |
| Auth | `Authorization: Bearer <API_SERVER_KEY>` from `compose/hermes/api-server.env` |

Re-apply after changing `api-server.env` or `HERMES_API_MAX_TURNS`:

```bash
docker compose run --rm hermes-api-bootstrap
docker compose restart hermes
```

### When the bootstrap runs

Compose starts both bootstrap containers again on every `docker compose up`, and `hermes` waits for them. A run is skipped in under a second when nothing has changed since the last complete run. The bootstrap compares two hashes with the stamps in `data/hermes/.bootstrap-stamps/`:

| Hash | Covers |
|---|---|
| Inputs, one per profile | `bootstrap-api-profile.sh`, the profile's env file (`api-server.env` or `browser.env`), the CalDAV account files, `HERMES_AGENT_IMAGE_TAG` and the image's `pyproject.toml`, and every environment variable the container gets |
| State, shared | `config.yaml`, `.env`, `.messages-webhook.json` and `.mail-cron-toolsets.json` in `data/hermes` and in every `data/hermes/profiles/<name>/` |

A changed input, a config edited by hand or by Hermes, or a profile added or removed runs the full bootstrap. A skipped run still writes the profile's `gateway_state.json`, the only file written on every start. `HERMES_BOOTSTRAP_FORCE=1` runs the full bootstrap anyway, and `make hermes-reload` sets it.

`hermes-api-bootstrap` configures the default profile and sweeps every profile. `hermes-browser-bootstrap` runs after it with `HERMES_BOOTSTRAP_SHARED=0` and configures only the `browser` profile.

### What hermes waits for at start

`hermes` starts once both bootstraps have finished and `hermes-worker` (ssh terminal backend), `llm-proxy` and `signal-cli` (with the `signal` profile) are healthy. It does not wait for its MCP sidecars: `lightrag-mcp`, `mcp-searxng`, `caldav-mcp`, `opencode-mcp`, `sql-mcp-ro`, `sql-mcp-rw`, `vikunja`, `mail-mcp`, `mail-drafts-mcp` and `messages-mcp`. One that is still booting when the gateway's startup discovery reaches it parks without its tools, and the next parked probe brings them back once it is up. The bootstrap sets that probe's interval on every MCP entry that points at a sidecar: `MCP_PARKED_RETRY_INTERVAL`, 15 s by default instead of Hermes' 300 s. An empty value keeps Hermes' default.

`docker compose up hermes` on its own does not start the sidecars; `docker compose up` does.

Starting next to the rest of the stack makes slow disk work in the container slower. The image's `01-hermes-setup` runs `chown -R` over `data/hermes/profiles/` whenever anything there is not owned by hermes, which took 55 s during a full start. The stack's `007-profile-ownership` step runs first: it removes sockets left at `gateway.sock` and `home/.config/browser-harness/runtime/` (both now on `/tmp`) and chowns the few foreign files itself, so the walk does not run.

For quick lookups via the API (n8n, curl, etc.), include a brief system message so the agent matches dashboard chat pacing. Hermes layers this on top of its core prompt (soft guidance — tools remain available):

```bash
curl http://localhost:8643/v1/chat/completions \
  -H "Authorization: Bearer $API_SERVER_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "api-server",
    "messages": [
      {
        "role": "system",
        "content": "Answer concisely in 2-4 sentences. Use web search only when you cannot answer from knowledge. At most one web search unless the user asks for deep research."
      },
      {"role": "user", "content": "What is LightRAG and how does it differ from vanilla RAG?"}
    ]
  }'
```

For long-running jobs, use `POST /v1/runs` and `POST /v1/runs/{run_id}/stop` to cancel cleanly instead of force-quitting.

## Local LLM config

Hermes does not hold the model key. Bootstrap sets every profile to the stack proxy:

```yaml
model:
  provider: custom
  model: your-chat-model   # match LLM_MODEL in .env
  base_url: http://llm-proxy:4000/v1
  api_key: "local-llm"     # placeholder; the real key stays on llm-proxy
```

`llm-proxy` reads `LLM_BINDING_HOST` and `LLM_BINDING_API_KEY` from the host `.env` and replaces the placeholder. LightRAG's own model uses `/lightrag/v1` on the same proxy. Embeddings use `/embed/v1`. The inference port is not published. A loopback admin API (`127.0.0.1:4001`, `POST /admin/upstreams`) can replace those upstreams in memory; a restart loads `.env` again. Nothing from that request is written to disk. To keep a key out of `.env` and `docker inspect`, set `LLM_BINDING_API_KEY_FILE` (or the `LIGHTRAG_`/`EMBEDDING_` equivalent) to a mounted file; `docker compose kill -s HUP llm-proxy` or `POST /admin/reload` re-reads it without a recreate. An app that starts the proxy with no key and pushes it at runtime is covered in [extending.md](extending.md#start-without-a-key).

The proxy forwards each streamed chunk as it arrives. `LLM_TIMEOUT` (default 600s) bounds the wait for the upstream's first response, which includes prompt prefill. Once a reply is streaming, `LLM_STREAM_IDLE_TIMEOUT` (default: `LLM_TIMEOUT`) bounds a silent gap; past it the proxy drops the connection, so Hermes sees a failed stream instead of waiting on a quiet one. When a client disconnects, the proxy closes the upstream request too, so a model server that runs one request at a time does not keep working on it.

Both of those timeouts watch for silence, so a model stuck in a loop that keeps producing tokens trips neither. Two more limits cover that. `LLM_DEFAULT_MAX_TOKENS` (default 16384) adds `max_tokens` to a `/chat/completions` or `/completions` request (`max_output_tokens` on `/responses`) that sets none of `max_tokens`, `max_completion_tokens` or `max_output_tokens`, on the chat and LightRAG routes. A request with its own limit is left alone. `LLM_STREAM_MAX_SECONDS` (default 3600) bounds one request from start to finish; past it the proxy drops the stream like an idle one and closes the upstream request, so LM Studio or Ollama stops generating. `0` turns either off. For LM Studio, also set the model's context overflow policy to stop at the limit: a rolling window lets one generation run past the context length.

Hermes treats the dotless `llm-proxy` host as a local server whatever is behind it. Bootstrap therefore sets `agent.local_stream_stale_timeout` on every profile, sized from `LLM_BINDING_HOST`: 300s for a local server, 180s for a cloud API (`HERMES_PROXY_STALE_TIMEOUT` overrides it). For a local upstream it also turns off WebUI auto-titling, because the title request would run before the reply on a server that handles one request at a time (`HERMES_BROWSER_AUTO_TITLE=1` keeps it). Every profile on the proxy that has no `model.max_tokens` gets `HERMES_MAX_TOKENS` (default 16384; `browser` keeps its 1024, and `0` writes nothing), so Hermes' own retries for a reply cut off at the limit start from that value. `HERMES_STREAM_RETRIES` defaults to 1 reconnect. An upstream pushed later through the admin API is not seen by bootstrap; run `make hermes-reload` after changing `LLM_BINDING_HOST`.

### Example: LM Studio

Enable **Serve on Local Network**, then set `LLM_BINDING_HOST` in `.env` to `http://host.docker.internal:<port>/v1` and `LLM_BINDING_API_KEY` to the server's key (any non-empty string for a local server). Leave Hermes on `http://llm-proxy:4000/v1`.

To switch models often, load the model in LM Studio and run:

```bash
./scripts/model-use.sh --from-lmstudio --lightrag same --restart
# interactive menu when multiple models are loaded; -y to auto-pick first chat model
# or: make model-use FROM_LMSTUDIO=1 LIGHTRAG=same RESTART=1
```

`LLM_MODEL` in `.env` is the stack's one model setting. GPT Researcher reads it through compose; Hermes and OpenCode keep the id in their own config, so the script copies it there: `model.default` and `model.model` in every Hermes profile (one container run for all of them), and the OpenCode default. A profile whose `model.base_url` is not `llm-proxy` has its own upstream and keeps its model. After editing `LLM_MODEL` by hand, run `make model-sync` (add `RESTART=1` to recreate services) to copy it out again.

Presets: copy `models.yaml.example` to `models.local.yaml`, then `make model-use PRESET=muse-glimmer`.

Sampling settings per model (temperature, top_k and the like) live in `model-defaults/local.json` and follow the model id, so `model-use` needs no extra step. See [Model defaults](model-defaults.md).

### Model suitability (agentic tool use)

Hermes WebUI sends a large system prompt plus the full tool schema (~20k input tokens). Models that work in a minimal OpenRouter “one tool” smoke test can still fail here.

| Model class | Agentic WebUI | Notes |
|---|---|---|
| Qwen 3.x (e.g. `qwen/qwen3-32b`, local Qwen via LM Studio) | Recommended | Strong structured `tool_calls` under this stack |
| GPT / Gemini / DeepSeek (via OpenRouter) | Usually fine | Covered by Hermes `tool_use_enforcement: auto` |
| Llama 3.x (e.g. `meta-llama/llama-3.3-70b-instruct` on OpenRouter) | Not recommended | Often emits `search_files(...)` or `<function/name=...>` as plain text (`tool_turns=0`), or OpenRouter returns an empty SSE body that retries replay from cache |

Prefer Qwen-class (or other known-good agentic) models for folder listing, MCP, and multi-step tool work. A direct OpenRouter curl with one tool is not a counterexample when Hermes’ full prompt is the failure context.

**Tool-use enforcement:** leave `agent.tool_use_enforcement` at `auto` (bootstrap default). Forcing `true` / stacking `execution_guidance` can help chatty models, but on weaker or quantized models it can make text-mimicked tool syntax *worse* ([Hermes #56360](https://github.com/NousResearch/hermes-agent/issues/56360)). Do not set those globally for OpenRouter Llama.

Hermes v0.22 no longer shows a reasoning-only reply as the answer on this stack's route (a custom provider behind llm-proxy); it re-prompts instead. `scripts/test-reasoning-promotion-gate.py --image` checks that on each bump.

### Automatically registered MCP servers

The `hermes-api-bootstrap` service registers these for you. Each one sets individual keys instead of replacing the whole `mcp_servers` mapping, so servers you added by hand survive.

| Server | Profiles | Tools exposed | Gate |
|---|---|---|---|
| `lightrag` | `api-server` / `browser` | `query_document`, `get_documents`, `get_pipeline_status`, `get_graph_labels`, `check_lightrag_health` | `LIGHTRAG_MCP_ENABLED=1` (`rag` profile; setup `--rag`) |
| `searxng` | default + `api-server` / `browser` | `searxng_web_search`, `web_url_read` | Always (on `core`) |
| `caldav-<slug>` | default + `api-server` / `browser` | Full 14 on default/browser; 8 read-only on `api-server` | `CALDAV_MCP_ENABLED=1` (`calendar` profile; setup `--calendar`) |
| `sql` | default + `api-server` / `browser` | `list_schemas`, `list_objects`, `get_object_details`, `execute_sql`, `explain_query`. `sql-mcp-ro` (`agent_ro`) on `api-server`, `sql-mcp-rw` (`agent_rw`) elsewhere | `SQL_MCP_ENABLED=1` (`db` profile; setup `--db`) |
| `opencode` | default + `browser` only | `coding_list_roots`, `coding_start_task`, `coding_get_task_status`, `coding_wait_for_task`, `coding_get_task_result`, `coding_continue_task` | `OPENCODE_MCP_ENABLED=1` (`coding` profile; setup `--coding`) |

These filters serve different purposes. LightRAG's and CalDAV's on `api-server` are **safety boundaries**: mutating tools do not belong in unattended n8n sessions. OpenCode coding tools are also mutating and are **never** registered on `api-server`. The `sql` entry draws its boundary in Postgres instead: the same five tools everywhere, but `api-server` connects as a role that can only read (see [Shared database](database.md)). The web filters just keep the tool count down, since both of those servers are read-only against the public internet.

CalDAV accounts live in `compose/caldav-mcp/accounts/<slug>.env`. Bootstrap registers each against the shared `caldav-mcp` sidecar. URL and username stay in the MCP headers. The password header is `${CALDAV_<SLUG>_PASSWORD}`, and the secret is copied into that profile's `.env` for Hermes to expand at connect time. Run `make hermes-reload` after changing accounts. See [Calendar](calendar.md).

Either way the filter must be a YAML list. A stringified `'["a","b"]'` gets misread as a one-element allowlist that no tool name matches, and zero tools get registered without any complaint. See the verification commands below.

`searxng` gives Hermes `web_url_read`, which reads one known URL as markdown without going through search. It does not execute JavaScript and it blocks private/internal URLs.

The `lightrag-mcp` image pins `lightrag_mcp==0.1.1` and patches its generated client to send LightRAG auth as `X-API-Key`, which is what current LightRAG servers expect.

After changing any of this, re-run both profile bootstraps and recreate `hermes`:

```bash
make hermes-reload
```

### Adding more by hand

Add further servers to `config.yaml` in `data/hermes/` (or `data/hermes/profiles/api-server/config.yaml`) after `hermes setup`, then run `/reload-mcp` in a session:

```yaml
mcp_servers:
  gptr:
    url: "http://gptr-mcp:8000/sse"
    transport: sse
    timeout: 300
    connect_timeout: 30
    tools:
      include: [deep_research, quick_search, write_report, get_research_sources]
```

A server that goes away for minutes at a time, such as one inside a desktop app, needs a shorter parked retry and a way to wake it. See [MCP servers your app hosts](extending.md#mcp-servers-your-app-hosts).

Ask Hermes to use LightRAG for Knowledge Base questions. Catalog / empty-check
prompts (“summarize what is in my Knowledge Base”) may use `get_documents` or
`get_graph_labels`. Content questions (“what does the KB say about X?”) should
call `query_document`. Prefer the KB before web search; if it is empty, say so.

**Web / research routing** (native `web_search` / `web_extract` are **disabled** via `agent.disabled_toolsets`. If a model invents those names anyway, dispatch **rewrites** them to MCP `searxng_web_search` / `web_url_read` when args are mappable — refusal alone caused retry loops on weaker tool-callers. Hermes does not inherit `SEARXNG_URL` — MCP uses `SEARXNG_MCP_URL`. `HERMES_ENVIRONMENT_HINT` reinforces the MCP path. Depending on `HERMES_WEB_SEARCH_MODE`, the searxng tools may be answered by Hermes' keyless ring instead of SearXNG; see [Search modes](searxng.md#search-modes)):

| Need | Tool | Notes |
|---|---|---|
| Knowledge base content | LightRAG `query_document` | Before any web search |
| Knowledge base catalog / empty / pipeline | LightRAG `get_documents` / `get_pipeline_status` | Health check only after a LightRAG call fails |
| Quick web fact | MCP `searxng_web_search` | **At most one** call unless the user asks for deep research; do not fan out query variants in parallel |
| Known URL | MCP `web_url_read` | No search fan-out; use this instead of native `web_extract`. On 403, use snippets or local browser. |
| Deep multi-step report | `gptr` (`deep_research` / `quick_search`) | Not a spray of SearXNG queries; avoid while LightRAG is indexing |
| Locate / diagnose a named repo | `coding_list_roots` then search the **host** path | Use the `delegate-coding` skill. Do not invent `/opt/projects/<guess>` when that slug is not an immediate child of `/opt/projects` — see [OpenCode](opencode.md#hermes-delegation) |
| Implement / refactor / tests in a repo | `coding_*` (OpenCode MCP) | Use the `delegate-coding` skill; path must be under a coding root — see [OpenCode](opencode.md#hermes-delegation) |

SearXNG itself is tuned to a lean Bing + Google CSE pair so each lookup hits fewer upstreams — see [SearXNG](searxng.md#empty-results--suspended-engines).

Only one LightRAG workspace is hot at a time (`WORKSPACE` in `.env`). Create and switch corpora with `make corpus-*` — see [Knowledge bases](knowledge-bases.md).

## Memory

Six places a fact can live. They are not interchangeable.

| Store | Job | Cap / scope |
|---|---|---|
| Native `memory` tool | Tiny durable facts (identity, standing prefs) injected every session | `USER.md` ~1375 chars, `MEMORY.md` ~2200 chars |
| `session_search` | What was said in a past chat | FTS over **that gateway's** `state.db` |
| `working-memory` skill | Long-form notes that will not fit the cap | files under `/opt/memory` |
| `living-todos` skill | Cross-session task list | Vikunja with the `todo` profile ([todo.md](todo.md)), else `/opt/projects/project-todo-list/README.md` |
| `database` skill | Structured rows: integration data, tables the agent keeps | shared Postgres, schema `agent` for its own (`db` profile) |
| LightRAG | Ingested documents | the hot `WORKSPACE` |

`session_search` is a native Hermes tool on both `hermes-cli` and `hermes-api-server`. There is no companion recall skill.

[Memory](memory.md) is the user-facing how-to (what to put where, remember / recall /
consolidate, troubleshooting).

### Built-in USER.md / MEMORY.md

Hermes already had this enabled. It stayed empty because the local model never
called the `memory` tool, and the factory `nudge_interval` of 10 almost never
fires on 1–2 turn chats. Bootstrap now sets:

| Profile | `memory.nudge_interval` | Why |
|---|---|---|
| default (dashboard / CLI) | 3 | interactive; review can fire on short chats |
| `browser` (WebUI) | 10 | local LM Studio has one slot; avoid turn-3/6 background review racing chat |
| `api-server` | 10 | unattended n8n one-shots must not distill themselves into USER.md |

Skill-library auto-review is **off** on interactive profiles (`skills.creation_nudge_interval=0` on default and `browser`). A finished or halted turn used to fork `bg-review` (“update the skill library”) and could hold the LLM stream for hours. Create skills explicitly; memory review stays on. Hermes CLI may warn that `skills.creation_nudge_interval` is unrecognized — `agent_init` still reads it; `0` stops automatic skill-library forks.

Hermes LLM HTTP calls (foreground and background) use `HERMES_API_TIMEOUT` (default **180s**) and `HERMES_API_CALL_STALE_TIMEOUT` (default **90s**) on the `hermes` service. Local endpoints skip implicit stale detection unless the stale value is set.

Set `TZ` in `.env` (IANA name, e.g. `America/Los_Angeles`) so container `date` and “Conversation started” agree. Compose defaults to UTC.

`flush_min_turns` is dead config in this agent tag. `memory.provider` stays empty
(built-in only; no Honcho / Mem0).

The three profiles each have their own Hermes home, so without extra mounts a
WebUI write would never appear on the dashboard. Compose overlays the default
store onto the other two:

```text
./data/hermes/memories  →  /opt/data/memories                  (default)
                        →  /opt/data/profiles/api-server/memories
                        →  /opt/data/profiles/browser/memories
```

`setup.sh` seeds `USER.md` once (empty Identity / Preferences / Working style
headings). `MEMORY.md` appears on the first tool write. Hand-edit `USER.md`;
it is a normal markdown file.

Ask explicitly when you want something saved: `Remember that I prefer terse replies.`

### Curated files (`working-memory`)

A repo-shipped skill, same pattern as `write-in-voice`. User-owned markdown for
people, decisions, preferences, and extra topic notes.

| Host | Container | Mode | Contents |
|---|---|---|---|
| `$ASSISTANT_DATA_ROOT/memory` | terminal backend `/opt/memory` | read-write | Curated long-form notes |


The skill routes: tiny facts → `memory` tool; past chats → `session_search`;

even when the bind is read-write.

## Conversational tone (SOUL.md)

How the agent *talks* in chat is a different file from how it *drafts* in your

this stack's wrinkle is that the three gateways do **not** share the file.

| Surface | Host path |

| WebUI (`browser` profile) | `data/hermes/profiles/browser/SOUL.md` |
| Dashboard / CLI (default) | `data/hermes/SOUL.md` |
| n8n API (`api-server`) | `data/hermes/profiles/api-server/SOUL.md` |

Compose overlays `USER.md` / `MEMORY.md` across those homes. It does **not**
overlay `SOUL.md`. Edit the browser copy for WebUI chat; copy the same text to
the default file if you want the dashboard to match. Leaving them diverged is
how you get a terse WebUI and a generic CLI.

Hand-edit the markdown. Keep it to identity, style, avoid, and defaults — a few
hundred words, not a manifesto. Absences belong in an **Avoid** list (no
preamble, no sycophancy, no hype). Then start a **new** WebUI thread; the
system prompt is built at session start, so continuing an old chat will not
pick up the edit. No Hermes restart is required.

`/personality` presets are session overlays on top of soul. Fine for a one-off
mode switch; a poor loop for shaping the baseline, and this lean WebUI (gateway
mode, no agent source in the UI container) is a weak place to drive them.

### Samples: distill, do not inject

Raw writing or chat samples belong on disk as a calibration corpus, not in the
prompt:

```text
$ASSISTANT_DATA_ROOT/voice/<name>/samples/   →   /opt/voice/<name>/samples/
```

That mount is already gitignored. Calibrate (or hand-write) a `STYLE.md`, then
copy the constraints that matter — especially the Avoid list — into the
browser `SOUL.md`. Keep chat transcripts in a **separate** voice directory from
essay/blog samples; mixed corpora wreck the sentence-length stats
`write-in-voice` uses.

Do not paste the corpus into `SOUL.md`, `USER.md`, `AGENTS.md`, or
`HERMES_ENVIRONMENT_HINT`. `SOUL.md` is on every completion (including
tool-follow-up calls). Hermes caps context files at a 20k-character floor and
truncates with a 70/20 head/tail split, so a dumped corpus both costs thousands
of tokens per request and loses its middle. On a local model that is prefill
time and conversation room, not API spend.

A one-liner in `USER.md` Preferences ("I prefer terse replies") is a cheap
user-side nudge. It does not replace soul.

## Writing in your voice

Hermes ships with a `write-in-voice` skill that drafts new text in your own writing style,
calibrated from samples you provide. Samples stay local and git never tracks them.
This skill does **not** change how the agent talks in WebUI or dashboard chat —
that is [SOUL.md](#conversational-tone-soulmd).

```bash
mkdir -p "$ASSISTANT_DATA_ROOT/voice/my-voice/samples"
cp ~/writing/*.md "$ASSISTANT_DATA_ROOT/voice/my-voice/samples/"
docker compose up -d
```

Then, in a Hermes session:

```text
Calibrate the my-voice writing voice.          # once, and after adding samples
Write a 600-word post about pricing in the my-voice voice.
```

Calibration writes `$ASSISTANT_DATA_ROOT/voice/my-voice/STYLE.md`, a distilled description of your style:
sentence rhythm, punctuation habits, vocabulary, and a "never does" list. Read and edit it.
Hand-correcting that file is the fastest way to improve output. Drafting then loads
`STYLE.md` plus two to four exemplars named in its frontmatter, and finishes with a
`humanizer` pass.

[How to generate text in your voice](writing-voice.md) walks through the whole process:
choosing a corpus, calibrating, editing `STYLE.md`, and troubleshooting.

Two mounts back all of this. Skills stay on `hermes` (and on the worker, read-only, when the terminal backend is ssh) so the process can load them. Voice files live on the terminal backend, where `write_file` runs:

| Host | Container | Mode | Contents |
|---|---|---|---|
| `./compose/hermes/skills` | `/opt/skills` on `hermes` and, in ssh mode, the worker | read-only | Repo-shipped skills (tracked in git) |
| `$ASSISTANT_DATA_ROOT/voice` | terminal backend `/opt/voice` | read-write | Your writing corpora |

The skills mount is read-only on purpose. Hermes treats `skills.external_dirs` purely as a
discovery path; it draws no write boundary there, so a writable directory is one the agent's
own skill-management tools can edit. The read-only flag is what keeps repo-shipped skills
pristine.

`hermes-api-bootstrap` registers `/opt/skills` in `skills.external_dirs` automatically, as a
YAML list, for both the default and `api-server` profiles. It never overwrites a list you
maintain yourself. If yours already contains `/opt/skills`, the bootstrap leaves it alone; if
it does not, you get a warning and add the entry yourself.

To register a directory by hand, edit the `config.yaml` of the profile you want —
`data/hermes/config.yaml` for the default, `data/hermes/profiles/api-server/config.yaml` for
the API profile — then restart:

```yaml
skills:
  external_dirs:
    - /opt/skills
    - /your/dir
```

```bash
docker compose restart hermes
```

Do not use `hermes config set` for this key. It stores its argument verbatim and cannot
produce a YAML list, so `'["/opt/skills"]'` lands as a quoted string. Hermes then treats the
whole `["/opt/skills"]` as one relative path, resolves it under `HERMES_HOME`, finds nothing,
and skips it with only a debug-level log. The skill never loads and nothing tells you why.

Notes:

- Skills are read at startup. If you add or edit one while the stack is running, restart
  with `docker compose restart hermes`.
- The drafting model sets the ceiling on output quality. Style matching is hard for small
  local models, and swapping in a bigger one usually beats piling on more samples.
- If Hermes cannot write into `/opt/voice`, check two things. `HERMES_WRITE_SAFE_ROOT`
  must list `/opt/voice` (this stack does) or `write_file` / `patch` refuse the path even
  though the write runs on the SSH worker. If the sandbox is already correct, the host
  directory is probably owned by root because Docker created it instead of `setup.sh`. Fix
  ownership, or set `HERMES_UID` and `HERMES_GID` in `.env` to your own `id -u` / `id -g`.

## SSH worker

`HERMES_TERMINAL_BACKEND` chooses where `terminal`, `read_file`, `write_file`, `search_files`, and `execute_code` run. The default is `ssh`. Unset means ssh, so an existing `.env` keeps the worker.

With `ssh`, those tools run on `hermes-worker`, a second container with sshd and no secrets. Bootstrap sets `terminal.backend` to `ssh` on the default profile, on the profile that bootstrap owns, and on every other directory under `data/hermes/profiles/`. New profiles cloned from default inherit it. `terminal.env_passthrough` is removed so the agent environment is not forwarded. The worker's sshd has `AcceptEnv none`. Bootstrap also sets `bot_desktop.placement` to `gateway`. Hermes's `auto` placement can otherwise start the browser on the worker, which has no Node or browser. Browser tools stay in `hermes`, next to the image's Chromium.

The worker image includes bash, GNU tar, python3, git, and ripgrep. Hermes runs each remote command with `bash -l`, and its session snapshot uses `tar --no-overwrite-dir`, which BusyBox tar does not support. `execute_code` needs python3 on the backend. `search_files` prefers `rg`.

`setup.sh` generates an ed25519 key under gitignored `compose/hermes/worker/ssh/` if it is missing. The private key is mounted read-only into `hermes` at `/opt/hermes-ssh/id_ed25519` (not under `/opt/data`). A startup script copies it to `/var/lib/hermes-worker-key/id_ed25519` with mode 600, which is the path `terminal.ssh_key` uses. The public key is the worker's `authorized_keys`. The worker has no host port and no `env_file`.

The worker mounts projects, voice, and memory read-write, the coding workspace at the same host path, and `/opt/skills` read-only. It does not mount `data/hermes`. MCP clients and the memory tool stay in `hermes`. `hermes-webui` keeps its own project, voice, and memory mounts so the picker and AGENTS.md prefill still read the host tree.

`/opt/projects` stays mounted **read-only** on `hermes` so `projects.list` and `projects.tree` can see the directory from inside the Hermes process. Writes to that path go through the worker, which has the same host directory read-write.

`make coding-root-add` and `make context-root-add` attach extra binds to `hermes-worker` (and OpenCode, for coding roots). `make ensure-local` moves roots listed in `CODING_EXTRA_ROOTS` and `CONTEXT_EXTRA_ROOTS` onto that service. `make doctor` warns when an absolute host path is still mounted on `hermes`.

After pulling this change, create the key if setup has not, then recreate so the mounts and the SSH config take effect:

```bash
./scripts/setup.sh
docker compose run --rm hermes-api-bootstrap
docker compose run --rm hermes-browser-bootstrap
docker compose up -d --force-recreate hermes-worker hermes
```

A working split looks like this: `terminal` `hostname` is `hermes-worker`, and a `write_file` under `/opt/projects` shows up on the host even though that mount is read-only inside `hermes`.

### Local escape hatch

`HERMES_TERMINAL_BACKEND=local` is for debugging, or for a machine that cannot run the extra container. Compose does not start `hermes-worker`, and `hermes` does not wait for it. Projects, voice, memory, and the coding workspace mount read-write on `hermes`. Bootstrap sets `terminal.backend` to `local`, removes leftover `terminal.ssh_*` keys, and sets `bot_desktop.placement` back to `auto`.

That puts the shell in the container that holds the dashboard password and profile secrets. Switch back to `ssh` when you are done.

```bash
# edit .env: HERMES_TERMINAL_BACKEND=local
make ensure-local
docker compose run --rm hermes-api-bootstrap
docker compose run --rm hermes-browser-bootstrap
docker compose up -d --force-recreate --remove-orphans hermes
```

`--remove-orphans` stops a worker left over from ssh mode. `make ensure-local` moves extra coding and context binds onto `hermes` and drops an empty `hermes-worker` block from `docker-compose.override.yml`, which would otherwise invent a service with no image.

## Per-project working directories

The worker gives Hermes somewhere to keep bodies of work that need reference material and
generated output side by side: a job search, a book, a client engagement, a research topic.

| Host | Where | Mode | Contents |
|---|---|---|---|
| `$ASSISTANT_DATA_ROOT/projects` | ssh: worker `/opt/projects` (read-write) and `hermes` `/opt/projects` (read-only, for `projects.list`). local: `hermes` `/opt/projects` read-write | split | Your per-project working directories |
| Host path in `CONTEXT_EXTRA_ROOTS` | terminal backend, same host path | read-only | Extra project file-context dirs (`make context-root-add`) |

Each subdirectory is one project. `setup.sh` creates the projects dir and drops a `README.md`
there. Scaffold a new project with `make project-init PROJECT=…`, keep a short `AGENTS.md`
brief and an `INDEX.md` file map, and select the path as a WebUI workspace when you want the
brief injected automatically. Full convention: [Projects](projects.md). Relocate the host
root with [User data directory](data-dir.md).

```bash
make project-init PROJECT=my-project
# optional extra host notes: edit sources.yaml, then
# make context-root-add DIR=/absolute/path && docker compose up -d --force-recreate hermes-worker
# (recreate hermes instead when HERMES_TERMINAL_BACKEND=local)
make project-index PROJECT=my-project
```

You can still reference a path in a prompt: `Using the notes in /opt/projects/my-project, draft ...`

You do not have to name the path every time. `HERMES_ENVIRONMENT_HINT` on the `hermes`
service describes the mount layout in the system prompt, so an **existing**
projects-library slug ("the career project") resolves to `/opt/projects/career`.
A name that is not an immediate child of `/opt/projects` is a coding-root
lookup (`coding_list_roots` + host path), not an invented
`/opt/projects/<guess>`. Do not drop that hint. Hermes probes its environment at
prompt-build time and reports only `/opt/data` as both home and working directory, so without
it the agent builds paths like `/opt/data/projects`, gets `Path not found`, and concludes the
folder does not exist even though the mount is perfectly healthy. Keep `/opt/projects` and
`/opt/memory` listed there when you add mounts of your own.

The hint is not enough by itself. The official image sets `HERMES_WRITE_SAFE_ROOT=/opt/data`,
so `write_file` and `patch` hard-block `/opt/projects` (and `/opt/voice`, `/opt/memory`) even
when the SSH worker has the directory read-write. The agent then treats that as "read-only"
and writes under `/opt/data/projects`, which lands in `data/hermes/` mixed with Hermes state.
Compose overrides the sandbox to `/opt/data:/opt/projects:/opt/voice:/opt/memory` plus coding
roots. Keep `/opt/data` first so cron, memories, and profile state still write. Add any
new writable worker path to that list; do not add `/opt/skills` or `CONTEXT_EXTRA_ROOTS`
(those notes mounts stay read-only). Recreate `hermes` after changing it — a restart
does not pick up a new env value. Do not remount projects at `/opt/data/projects`, and do
not ask the agent to remember that path: the hint will keep sending it to `/opt/projects`.

The mount is live, so added files appear immediately and no restart is needed. Hermes can
write here, so keep source material you wrote in different subdirectories from drafts the
agent produced. Mix them and generated text starts coming back to you cited as fact, and you
lose the ability to ingest just the source half into LightRAG later. The same root-ownership
caveat as `/opt/voice` applies.

## Browser tools

Since Hermes v0.22.7 the browser is `browser_exec` (Python run by browser-harness), plus `browser_cdp`, `browser_dialog` and the `browser_vault_*` tools. The older `browser_navigate`, `browser_snapshot`, `browser_click` and related tools and the `agent-browser` CLI are gone upstream. A local browser is the Chromium build shipped in the image under `/opt/hermes/tools`, which is the container filesystem, so it is executable without a boot-time install. `./scripts/doctor.sh` checks that the `hermes` user can run it.

`browser_exec` runs browser-harness, which keeps one control socket per session (`bu-default.sock`, `bu-<name>.sock`). Its default location is `$HOME/.config/browser-harness/runtime`, which for the `hermes` user is under `data/hermes`. On that mount (virtiofs on Docker Desktop), a socket that outlives a Docker VM restart (quitting Docker Desktop, a crash, or a Mac reboot) becomes unreadable from inside the new VM: `ls -la` shows `s?????????`, and both connecting and deleting fail with `[Errno 95] Operation not supported: '…/bu-default.sock'`. Every call for that session then fails. macOS still sees a normal socket and can delete it. Recreating or restarting the container alone does not trigger this, but the stack keeps the sockets off the mount so that a VM restart can't either. The `hermes` service sets `BH_RUNTIME_DIR=/tmp/browser-harness` (with `BH_RUNTIME_DIR_SHARED=1` so session names stay in the filenames), which is the container filesystem. Logs and screenshots stay under `data/hermes/home/.config/browser-harness/tmp`.

The agent cannot clear a stuck socket itself: its terminal runs on `hermes-worker`, which does not mount `data/hermes`. If the error appears, check that the variable is set, recreate the container, and remove any sockets still on the host:

```bash
docker compose exec -u hermes hermes printenv BH_RUNTIME_DIR
docker compose up -d hermes
rm -f data/hermes/home/.config/browser-harness/runtime/*.sock data/hermes/home/.config/browser-harness/runtime/*.pid
```

`./scripts/doctor.sh` checks the variable and warns about leftover sockets.

The `hermes` service sets `UV_CACHE_DIR=/opt/uv-cache`, a named volume (`hermes_uv_cache`) shared by every profile and by Hermes' package manager, so uv's cache stays off the `data/hermes` mount, where uv is slow on Docker Desktop. `11-warmup-uv-cache` makes the volume writable by the `hermes` user at start. Before Hermes v0.22.7 it also fetched browser-use into it for `browser_exec`; v0.22.7 runs browser-harness from its own venv. `HERMES_UV_CACHE_DIR` mounts a host path there instead.

### Saving logins

Since v0.22 the vault is one tool, `browser_vault`, with an `action` argument (`list`, `fill`, `save_login`, `enter_code`, `unlock`); the separate `browser_vault_*` tools are gone. `save_login` saves a login for the origin of the page that is open, so the sign-in page has to be open first; otherwise it returns "Open the site's login page first". The repo skill `browser-login` (`compose/hermes/skills/browser-login/`) gives the order: open the sign-in page, `list`, `fill` a saved login or `save_login`, and never ask for a password in chat. The tool-eval case `browser-login-save-first` checks that a model follows it; eval traces record vault calls as `browser_vault.<action>`.

The repo skill `browser-signup` covers creating an account: ask for the identifier and profile fields before opening the page, ask before ticking terms boxes, `create_login` on the password step, `enter_code` or the user for verification, stop at a CAPTCHA, and `capture_secret` for an API key the site then shows. A client that wants a particular site or a follow-on step passes them in its own prompt. The cases `browser-signup-asks-first`, `browser-signup-create-login` and `browser-signup-captcha` check it.

### Creating logins on sign-up forms

The stack adds a sixth action, `create_login`, for a sign-up form whose password fields are open. The model passes the `identifier` the user chose (and optionally a `label`). Hermes sends the viewer the `vault.create_login` server request with `{origin, site, identifier, regenerate}`. The answer is a JSON string: `{"generate": true}` approves a generated password, `{"password": "..."}` carries one the user typed, and an empty string declines (`save_declined`). A card left unanswered for 180 seconds also counts as a decline. A session with no viewer that can answer (API server, cron) returns `prompt_unavailable` without sending the request.

The generated password is 24 characters with at least one lowercase letter, uppercase letter, digit and symbol (`-_.!@#%+=?`), shortened to the fields' `maxlength` and lengthened to their `minlength`. A `passwordrules` attribute replaces the character sets and can set the length and `max-consecutive`. The fill script checks each field's `pattern` in the page before writing anything. When the pattern refuses a candidate, Hermes retries without symbols and at 20, 16 and 12 characters, and returns `password_rules_unmet` if all eight attempts fail.

The targets are the password inputs marked `autocomplete="new-password"`, in the form of the first one. When the page marks none, they are the visible password inputs not marked or labelled as the current password, in the form that looks most like a sign-up: one with two password fields beats one with a single field, and create, confirm or repeat wording breaks a tie. A sign-in box in the page header or sidebar is left alone. Every target gets the same value, so a confirm field is filled too. The login is stored only after every target took the value; if storing fails the fields are cleared. The result holds the handle, origin, identifier and fill count, never the password, and the value is registered for redaction before it reaches the page, so a later `browser_exec` that reads the field gets `«redacted-vault-secret»`.

Calling `create_login` again with the returned `handle` sends the request with `regenerate: true`, then replaces that item's password and refills the form, for a site that rejected the first one after submit. Only items in the local vault can be regenerated; nothing is written to 1Password or Bitwarden. Items are bound to the sign-up page's origin, so a site that signs in on another host needs the login saved there with `save_login`.

`scripts/test-vault-create-login.py` checks the policy, the generator and the field selection on the host, and with the image present it runs the action in the image's Chromium against fixture pages through `browser_vault`'s dispatcher and the session prompt scope.

### Capturing keys from a page

`capture_secret`, the seventh action, stores a value the open page shows, such as an API key a dashboard displays once, without the model reading it. The model passes `name` (an environment-variable name such as `PREM_API_KEY`) and `destination`. Hermes reads the page over the supervisor socket and keeps values that are 20 to 4096 characters with no spaces, made of key characters, and either start with a known key prefix (`sk-`, `pk_`, `ghp_`, `xoxb-` and others) or mix letters and digits with high entropy. It looks in inputs and text areas (read-only ones too), and in `code`, `pre`, `kbd`, `samp` and other elements with no child elements. URLs, paths and e-mail addresses are skipped. With one match it uses that value. With several it returns them numbered, each with where it is on the page and its last four characters, and the model calls again with `candidate`. A `selector` names the element directly; an editable password input is refused there too (`password_field`), so a password typed or filled into the page is never copied out. Every value read is registered for redaction straight away, so a later `browser_exec` that prints the page shows `«redacted-vault-secret»`.

The viewer then gets the `vault.capture_secret` server request with `{origin, site, name, destination, last4, replaces, capture_id}`, which never contains the value. `"approve"` or `{"approve": true}` approves; anything else, or no answer within 180 seconds, declines (`save_declined`). Sessions with no viewer return `prompt_unavailable`.

- `destination: env` saves the value in the profile `.env` with `save_env_value_secure`, the call the `secret` card uses, so a provider key also reaches the credential pool. `replaces` is true when the name already has a value. Names that would change how Hermes or a tool connects or runs are refused before anything is read: `HERMES_*`, `API_SERVER_*`, `GATEWAY_*`, `LD_*`, `PYTHON*` and similar prefixes, names ending in `_URL`, `_HOST`, `_PORT`, `_PROXY`, `_PATH` or `_DIR`, and `PATH`, `HOME` and the proxy variables.
- `destination: viewer` writes the value to `vault/captured.json.enc` in the profile, encrypted with the vault's key, under `capture_id`. These captures are kept out of the vault itself, so `vault.list` and `browser_vault` `list` never show them. The client calls the `vault.take` RPC with `{id: capture_id}` once the tool result arrives. It returns `{name, origin, value}` and deletes the capture. A capture that is unknown, already taken or older than an hour is a `5095` error. `vault.take` is the one vault method whose result holds a secret. The value is never sent in a server→client frame: those go to every viewer attached to the session and are replayed to one that reconnects.

The tool result holds `name`, `destination`, `origin`, `last4`, `length`, `replaced` and, for `viewer`, `capture_id`. `scripts/test-vault-capture-secret.py` checks the value heuristics and name rules on the host, and with the image present it runs both destinations, several candidates, a decline and `vault.take` in the image's Chromium.

`browser_vault` `save_login` stores into Hermes' local vault (`vault_` handles) on every profile, including those with the Bitwarden add-on. With `BITWARDEN_ENABLED=1`, Bitwarden logins come from the `bwbroker` backend: `bwbroker:<slug>/<item id>` handles in `browser_vault` `list`, filled by the broker so the gateway never holds the value, and two tools, `bitwarden_request_access` and `bitwarden_release_access`, for asking for a login and giving one back. The bootstrap writes `vault.bitwarden.enabled: false` so Hermes' own `bw:` backend stays off. See [docs/bitwarden.md](bitwarden.md).
