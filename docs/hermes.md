# Hermes Agent

Persistent AI gateway with a web dashboard, an OpenAI-compatible API, skills, and memory. Ships in the default **`core`** profile.

[Hermes Agent](https://github.com/NousResearch/hermes-agent) runs as a persistent AI gateway with a web dashboard. It divides the work with OpenCode: Hermes takes messaging integrations and general agent workflows (skills, memory, scheduled jobs), while OpenCode sticks to coding in an isolated sandbox (`coding` profile).

## Enabling Hermes

Hermes starts whenever `core` is in `COMPOSE_PROFILES` (setup sets this by default):

```bash
# In .env (see .env.example)
COMPOSE_PROFILES=core
```

Then:

```bash
docker compose up -d
```

Remove `core` from `COMPOSE_PROFILES` to turn Hermes off. If it is already running, also run `docker compose down` or `docker compose stop hermes hermes-webui`.

You can combine profiles (`COMPOSE_PROFILES=core,rag,searxng-prod` or `--profile core --profile rag`).

## First-time setup

1. Run `./scripts/setup.sh` (creates Hermes env files and sets `COMPOSE_PROFILES=core`).
2. Run the setup wizard (writes config to `data/hermes/` on the host):
   ```bash
   docker compose run --rm hermes setup
   ```
3. Start the stack (bootstrap runs automatically, then the gateway):
   ```bash
   docker compose up -d
   ```
4. Open `http://localhost:9119` for the dashboard and sign in with `HERMES_DASHBOARD_USER` / `HERMES_DASHBOARD_PASSWORD` from `.env` (generated by `setup.sh`).

   Since agent 0.20.0 those credentials are mandatory rather than a hardening option. Inside the container the dashboard binds `0.0.0.0` (the host port is what keeps it local), and a non-loopback bind engages an auth gate that the old `HERMES_DASHBOARD_INSECURE=1` escape hatch no longer opens. With no auth provider registered the dashboard refuses to bind at all, and since the `hermes` healthcheck probes the dashboard, the container never turns healthy.

5. Chat UI is included on `core`: see [docs/hermes-webui.md](hermes-webui.md) (`http://localhost:8787`).

**Migrating from root `.env` API settings:** if you previously set `API_SERVER_ENABLED`, `API_SERVER_HOST`, or `API_SERVER_KEY` in `.env`, remove those lines and move `API_SERVER_KEY` into `compose/hermes/api-server.env`. The default profile no longer exposes an API on port 8642.

## API server profile (`api-server`)

A one-shot `hermes-api-bootstrap` service runs ahead of the main Hermes container, creating or updating an isolated **`api-server`** profile with:

| Setting | Value |
|---|---|
| Port | **8643** (`HERMES_API_SERVER_PORT`) |
| Max tool turns | **20** (`HERMES_API_MAX_TURNS`) |
| Tools | **`hermes-api-server`** (aligned with dashboard chat; no interactive-only tools) |
| Default profile API | **disabled** (dashboard/gateway on 8642 only) |

| Endpoint | URL |
|---|---|
| Host API | `http://localhost:8643/v1` |
| Compose network (n8n) | `http://hermes:8643/v1` |
| Auth | `Authorization: Bearer <API_SERVER_KEY>` from `compose/hermes/api-server.env` |

Re-apply after changing `api-server.env` or `HERMES_API_MAX_TURNS` (one-shot containers do not re-run on every `up`):

```bash
docker compose run --rm hermes-api-bootstrap
docker compose restart hermes
```

For quick lookups via the API (n8n, curl, etc.), include a brief system message so the agent matches dashboard chat pacing. Hermes layers this on top of its core prompt (soft guidance — tools remain available):

```bash
curl http://localhost:8643/v1/chat/completions \
  -H "Authorization: Bearer $API_SERVER_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "api-server",
    "messages": [
      {
        "role": "system",
        "content": "Answer concisely in 2-4 sentences. Use web search only when you cannot answer from knowledge. At most one web search unless the user asks for deep research."
      },
      {"role": "user", "content": "What is LightRAG and how does it differ from vanilla RAG?"}
    ]
  }'
```

For long-running jobs, use `POST /v1/runs` and `POST /v1/runs/{run_id}/stop` to cancel cleanly instead of force-quitting.

## Local LLM config

After setup, configure the model in the dashboard or in `data/hermes/config.yaml` to point at the same OpenAI-compatible server as LightRAG and OpenCode:

```yaml
model:
  provider: custom
  model: your-chat-model   # match LLM_MODEL in .env
  base_url: http://host.docker.internal:1234/v1
  api_key: "local-llm"     # any non-empty string for most local servers
```

### Example: LM Studio

Enable **Serve on Local Network**, then set `model` to the id LM Studio serves and `base_url` to `http://host.docker.internal:<port>/v1`.

## Optional internal integrations

From inside the Hermes container, other stack services are reachable by compose DNS name:

| Service | Internal URL | Notes |
|---|---|---|
| SearXNG | `http://searxng:8080/search?q=...&format=json` | Quick web search |
| GPT Researcher REST | `http://gpt-researcher:8000/report/` | Deep research via POST; long-running |
| gptr-mcp (SSE) | `http://gptr-mcp:8000/sse` | MCP tools: `deep_research`, `quick_search`, `write_report`, etc. |
| lightrag-mcp | `http://lightrag-mcp:8000/mcp` | MCP tools for LightRAG Knowledge Base queries |
| mcp-searxng | `http://mcp-searxng:3000/mcp` | MCP tools: `searxng_web_search`, `web_url_read` (read one URL as markdown) |
| LightRAG | `http://lightrag:9621/query` | Header Auth: `X-API-Key: $LIGHTRAG_API_KEY` |
| n8n | `http://n8n:5678` | Workflows can call Hermes API at `http://hermes:8643/v1` |

### Automatically registered MCP servers

The `hermes-api-bootstrap` service registers these for you. Each one sets individual keys instead of replacing the whole `mcp_servers` mapping, so servers you added by hand survive.

| Server | Profiles | Tools exposed | Gate |
|---|---|---|---|
| `lightrag` | `api-server` / `browser` | `query_document`, `get_documents`, `get_pipeline_status`, `get_graph_labels`, `check_lightrag_health` | `LIGHTRAG_MCP_ENABLED=1` (`rag` profile; setup `--rag`) |
| `searxng` | default + `api-server` / `browser` | `searxng_web_search`, `web_url_read` | Always (on `core`) |

These two filters serve different purposes. LightRAG's is a **safety boundary**: that server exposes 17 tools, and the 12 not listed above mutate the knowledge graph, `delete_by_doc_ids` and `delete_by_entities` among them. None of those belong in an unattended API session. The web filters just keep the tool count down, since both of those servers are read-only against the public internet.

Either way the filter must be a YAML list. A stringified `'["a","b"]'` gets misread as a one-element allowlist that no tool name matches, and zero tools get registered without any complaint. See the verification commands below.

`searxng` gives Hermes `web_url_read`, which reads one known URL as markdown without going through search. It does not execute JavaScript and it blocks private/internal URLs.

The `lightrag-mcp` image pins `lightrag_mcp==0.1.1` and patches its generated client to send LightRAG auth as `X-API-Key`, which is what current LightRAG servers expect.

The bootstrap is a one-shot container and does not re-run on every `up`. After changing any of this, re-run it:

```bash
docker compose run --rm hermes-api-bootstrap
docker compose restart hermes
```

### Adding more by hand

Add further servers to `config.yaml` in `data/hermes/` (or `data/hermes/profiles/api-server/config.yaml`) after `hermes setup`, then run `/reload-mcp` in a session:

```yaml
mcp_servers:
  gptr:
    url: "http://gptr-mcp:8000/sse"
    transport: sse
    timeout: 300
    connect_timeout: 30
    tools:
      include: [deep_research, quick_search, write_report, get_research_sources]
```

Ask Hermes to use LightRAG for Knowledge Base questions, for example: "Use LightRAG to summarize what is in my Knowledge Base." Use SearXNG for quick lookups and `web_url_read` to read a specific page; use `gptr` MCP for deep research. Avoid `deep_research` while LightRAG is indexing.

## Writing in your voice

Hermes ships with a `write-in-voice` skill that drafts new text in your own writing style,
calibrated from samples you provide. Samples stay local and git never tracks them.

```bash
mkdir -p data/voice/my-voice/samples
cp ~/writing/*.md data/voice/my-voice/samples/
docker compose up -d
```

Then, in a Hermes session:

```text
Calibrate the my-voice writing voice.          # once, and after adding samples
Write a 600-word post about pricing in the my-voice voice.
```

Calibration writes `data/voice/my-voice/STYLE.md`, a distilled description of your style:
sentence rhythm, punctuation habits, vocabulary, and a "never does" list. Read and edit it.
Hand-correcting that file is the fastest way to improve output. Drafting then loads
`STYLE.md` plus two to four exemplars named in its frontmatter, and finishes with a
`humanizer` pass.

[How to generate text in your voice](writing-voice.md) walks through the whole process:
choosing a corpus, calibrating, editing `STYLE.md`, and troubleshooting.

Two mounts on the `hermes` service back all of this:

| Host | Container | Mode | Contents |
|---|---|---|---|
| `./compose/hermes/skills` | `/opt/skills` | read-only | Repo-shipped skills (tracked in git) |
| `./data/voice` | `/opt/voice` | read-write | Your writing corpora (gitignored) |

The skills mount is read-only on purpose. Hermes treats `skills.external_dirs` purely as a
discovery path; it draws no write boundary there, so a writable directory is one the agent's
own skill-management tools can edit. The read-only flag is what keeps repo-shipped skills
pristine.

`hermes-api-bootstrap` registers `/opt/skills` in `skills.external_dirs` automatically, as a
YAML list, for both the default and `api-server` profiles. It never overwrites a list you
maintain yourself. If yours already contains `/opt/skills`, the bootstrap leaves it alone; if
it does not, you get a warning and add the entry yourself.

To register a directory by hand, edit the `config.yaml` of the profile you want —
`data/hermes/config.yaml` for the default, `data/hermes/profiles/api-server/config.yaml` for
the API profile — then restart:

```yaml
skills:
  external_dirs:
    - /opt/skills
    - /your/dir
```

```bash
docker compose restart hermes
```

Do not use `hermes config set` for this key. It stores its argument verbatim and cannot
produce a YAML list, so `'["/opt/skills"]'` lands as a quoted string. Hermes then treats the
whole `["/opt/skills"]` as one relative path, resolves it under `HERMES_HOME`, finds nothing,
and skips it with only a debug-level log. The skill never loads and nothing tells you why.

Notes:

- Skills are read at startup. If you add or edit one while the stack is running, restart
  with `docker compose restart hermes`.
- The drafting model sets the ceiling on output quality. Style matching is hard for small
  local models, and swapping in a bigger one usually beats piling on more samples.
- If Hermes cannot write into `/opt/voice`, the host directory is probably owned by root
  because Docker created it instead of `setup.sh`. Fix ownership, or set `HERMES_UID` and
  `HERMES_GID` in `.env` to your own `id -u` / `id -g`.

## Per-project working directories

A third mount gives Hermes somewhere to keep bodies of work that need reference material and
generated output side by side: a job search, a book, a client engagement, a research topic.

| Host | Container | Mode | Contents |
|---|---|---|---|
| `./data/projects` | `/opt/projects` | read-write | Your per-project working directories (gitignored) |

Each subdirectory is one project, structured however the work wants. `setup.sh` creates
`data/projects/` and drops a `README.md` there explaining the convention.

```bash
mkdir -p data/projects/my-project
```

Then reference it by path in a prompt: `Using the notes in /opt/projects/my-project, draft ...`

You do not have to name the path every time. `HERMES_ENVIRONMENT_HINT` on the `hermes`
service describes the mount layout in the system prompt, so "the career project" resolves to
`/opt/projects/career` on its own. Do not drop that hint. Hermes probes its environment at
prompt-build time and reports only `/opt/data` as both home and working directory, so without
it the agent builds paths like `/opt/data/projects`, gets `Path not found`, and concludes the
folder does not exist even though the mount is perfectly healthy. Keep `/opt/projects` listed
there when you add mounts of your own.

The mount is live, so added files appear immediately and no restart is needed. Hermes can
write here, so keep source material you wrote in different subdirectories from drafts the
agent produced. Mix them and generated text starts coming back to you cited as fact, and you
lose the ability to ingest just the source half into LightRAG later. The same root-ownership
caveat as `/opt/voice` applies.

## Advanced options

- **Terminal Docker sandbox** — mount `/var/run/docker.sock` and set `terminal.backend: docker` in Hermes `config.yaml` so shell commands run in an isolated container.

## Verification

```bash
docker compose ps    # omit --profile if COMPOSE_PROFILES=core in .env
# 302 to the login page is success here; the dashboard is behind basic auth.
curl -sf http://localhost:9119/ >/dev/null && echo "dashboard ok"

# LightRAG MCP sidecar is internal-only; requires the `rag` profile.
docker compose exec lightrag-mcp python -c "import socket; s = socket.create_connection(('127.0.0.1', 8000), 5); s.close(); print('lightrag-mcp ok')"

# Default profile: no API on 8642
curl -sf http://localhost:8642/health || echo "expected: no API on default port"

# API profile on 8643 (set API_SERVER_KEY from compose/hermes/api-server.env)
curl -sf http://localhost:8643/health && echo "api-server health ok"
curl -sf http://localhost:8643/v1/models -H "Authorization: Bearer $API_SERVER_KEY"
curl -sf http://localhost:8643/v1/toolsets -H "Authorization: Bearer $API_SERVER_KEY"

docker compose logs hermes-api-bootstrap | grep -F "Registering SearXNG MCP server"
# With rag enabled (LIGHTRAG_MCP_ENABLED=1):
docker compose logs hermes-api-bootstrap | grep -F "Registering LightRAG MCP server" || echo "skipped unless rag profile"

# LightRAG tool filter: must report "5 selected", not "all". The API profile is
# restricted to read-oriented tools, and "all" means the restriction is not applying.
# searxng must report "2 selected" on both profiles (web_url_read, searxng_web_search).
docker compose exec hermes hermes mcp list
docker compose exec hermes hermes -p api-server mcp list

# The filter must be a YAML list. If this prints the tool names one character at a
# time, it was stored as a string and zero LightRAG tools are registered.
docker compose exec hermes hermes -p api-server tools list | grep -A1 'MCP servers'

# Keys must not have compounded (mcp_servers.mcp_servers.searxng.url.timeout and
# similar) — that is what a variable collision in the bootstrap helpers looks like.
grep -A6 'mcp_servers:' data/hermes/config.yaml

docker compose logs -f hermes

# Writing voice: external_dirs must be a YAML list containing /opt/skills.
# A quoted '["/opt/skills"]' means the skill never loads, so watch for the
# leading "- " in this output.
docker compose exec hermes hermes config get skills.external_dirs
grep -A3 '^skills:' data/hermes/config.yaml data/hermes/profiles/api-server/config.yaml
docker compose exec hermes ls /opt/skills/write-in-voice

# Whether the skill is actually discovered. This is the one to trust.
docker compose exec hermes hermes skills list | grep write-in-voice

# Mount flags: /opt/skills must be ro, /opt/voice and /opt/projects must be rw
docker compose exec hermes sh -c 'grep -E " /opt/(skills|voice|projects) " /proc/mounts'

# Effective permissions for the user Hermes actually runs as
for d in /opt/voice /opt/projects /opt/skills; do
  docker compose exec --user hermes hermes \
    sh -c "test -w $d && echo '$d WRITABLE' || echo '$d NOT-WRITABLE'"
done
```
